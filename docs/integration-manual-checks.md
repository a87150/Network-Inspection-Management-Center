# 导入与外部连接：需要实机验证的清单

这一轮审查覆盖了文件导入、告警投递、人员目录同步、设备采集与门禁四条链路。
代码层面能确认的已经修掉，下面这些**只能在真实环境里定论**——要么依赖对端 API 的
实际字段，要么依赖设备/平台的实际行为，读代码推不出来。

每条都写了怎么验、以及验完要改哪里。没验之前，相关功能的行为是**未知**，不是**正常**。

## 一、飞书人员同步的入职日期

现象：`net/people/directory/feishu.py:240` 读的是 `hire_date`/`join_date` 两个键，
但飞书 v3 的用户对象里这两个键都不存在——入职时间在 `join_time`，是 Unix 秒。

要验的：
1. 接一个真实的飞书企业，同步一次。
2. 查 `People` 表里 `hire_date is null` 的比例。
3. 如果确实全空，抓一次 `contact/v3/users` 的原始响应，确认用户对象里到底有什么时间字段。

验完要改的：`_person_record` 里加 `join_time` 解析（Unix 秒 → 日期），或按抓到的真实字段名改。

影响：飞书来源的「当年入职人数」「平均司龄」恒为 0（`assets/overview.py:19-20`）。

## 二、飞书根部门 ID 的形态

现象：适配器固定用 `open_department_id`（`feishu.py:157/186`），而飞书后台界面上显示的是
数字形式的部门 ID。管理员照着后台填进「根部门」，同步就会读不到任何部门。

要验的：
1. 在飞书后台找一处显示部门 ID 的地方，记下它长什么样（`od-xxxx` 还是纯数字）。
2. 用这个值填进 `PeopleSyncSource.root_department_ids`，点「测试连接」。
3. 如果失败，换成 `open_department_id`（一般要通过 API 或 URL 里的另一段拿到）再试。

验完要改的：如果两种 ID 都存在，配置页应同时接受并自动判别，而不是只在文档里写一句。

## 三、钉钉/飞书的业务错误码

现象：`_success_code` 只判「是否等于 0」，分类只看 HTTP 401/403。而这两家都是
HTTP 200 + 业务错误码，所以权限不足、token 失效、限流、参数错误全部落进同一个
「人员目录连接失败，请检查网络和平台接口」。

要验的（每种造一次，记录实际返回码）：
1. 应用未开通通讯录读权限——飞书 `99991672`、钉钉 `60011`。
2. token 失效——飞书 `99991663`。
3. 根部门 ID 不存在——两家各自的码。
4. 触发限流——两家的频率错误码。

验完要改的：按码分类抛 `DirectoryAuthenticationError` / `DirectoryRateLimitError` /
`DirectoryPermissionError`，把「去查网络」变成「去开权限」或「重新授权」。

## 四、SNMP 设备的厂商温度 OID

现象：厂商温度 OID 有时返回 0/1 状态码或十分之一度。已修的部分是排除 0 和 1，
但**十分之一度**这一种没法从代码判断——同样的数值 450 既可能是 45.0℃（十分之一度），
也可能是 450℃（异常读数）。

要验的：
1. 挑几台不同厂商的设备，读它们的温度 OID 原始值。
2. 和设备面板上显示的温度对照，判断是整数度还是十分之一度。
3. 顺带确认 `ifHighSpeed` 在这几台设备上会不会返回 0（已经按「0 就回退 ifSpeed」处理，
   但要确认这个回退在真实设备上取到的值是对的）。

验完要改的：如果确实存在十分之一度的厂商，按厂商加一个倍数修正，而不是靠区间猜。

## 五、Excel 模板的日期列

现象：用「下载 Excel 模板」填人员表，在「入职日期」里输入 2026-01-15，Excel 会存成
日期型（`<v>46037</v>` + 样式），而 `_cell_value` 只取 `<v>` 文本，导入报
「time data '46037' does not match format」。**模板对人员实际不可用**。

要验的：
1. 用 Excel（不是 LibreOffice）打开下载的模板，填一个日期，保存。
2. 导入，看是否复现。
3. 用「文本」格式填同一个日期，再导一次，确认这条路径是通的。

验完要改的：`xlsx.py` 需要读 `cell/@s` 对应的 `numFmt`，判断是不是日期格式，
再把序列号转成日期。这是本轮**没修**的问题里最影响实际使用的一条。

## 六、告警渠道的真实限流阈值

现象：投递泵零限流，worker 每轮 4 条、间隔 5 秒，约 47 条/分钟，是钉钉单机器人
20 条/分钟上限的 2.3 倍。重试固定 30 秒且所有重试行同秒齐发。

要验的：
1. 接一个真实钉钉机器人，构造 60 条待投递告警。
2. 观察返回码（限流时是 `130101`），记录实际被限的条数。
3. 确认 30 秒后重试是否还在同一个限流窗口里。

验完要改的：加按渠道的节流（令牌桶或 `next_allowed_at`），重试改指数退避。
阈值要用实测值，不要照文档抄。

## 七、人员目录的限流重试

现象：429 的三次尝试在同一毫秒内打完（`dingtalk.py:233` 的 `continue` 之前没有 sleep），
`max_retries` 形同虚设；5xx 一次就放弃。遍历稍大的组织很容易撞平台 QPS 上限。

要验的：
1. 找一个部门数在几十以上的真实组织，完整同步一次。
2. 记录是否出现 429，以及出现在第几次请求。
3. 如果出现了，确认当前实现是否直接整次失败（快照全丢）。

验完要改的：加重试退避 + 读 `Retry-After`，5xx 也要重试。

## 八、门禁平台的事件量

现象：`MAX_PAGES=100 × PAGE_SIZE=1000` 看起来允许 10 万条，但 `adapters.py:151` 的硬闸是
10000 条，且判定点在第 10 页之后——超限即整批丢弃，`cursor_at` 不前进，
而重放窗口来自任务参数快照，同一任务重试永远超限。

要验的：
1. 接一个真实的 V6600 实例，选一个高峰时段（比如上班 8:00-9:00）做一次同步。
2. 看实际事件量落在什么量级。
3. 如果接近或超过 10000，确认任务是否卡死、需要人工重建。

验完要改的：改成分批续传（按时间窗切分 + `cursor_at` 前进），而不是拉完再判超限。

## 九、设备 API 的响应体积

现象：`http_collectors.py:26` 的响应没有字节上限，只有 12 秒超时。误配的 `api_url`
指向大文件时会把整包读进巡检进程（`response.text` 解码一次、`response.json()` 再解析一次）。

要验的：
1. 找一台正常设备，看它 `api_url` 返回体的实际大小。
2. 确认巡检 worker 在采这类设备时的内存占用基线。

验完要改的：加 `MAX_RESPONSE_BYTES` 逐块校验，和 `native_http.py:63-69` 的写法对齐。
现在这条没修是因为不知道合理的上限该设多少——设小了会截断正常响应。
